## 1. 진단 배경 — 실제 실패 사례 2건

이번 정비는 이론이 아니라 **당일 발생한 실제 실패**가 트리거였다.

| 실패 | 무슨 일이 벌어졌나 | 근본 원인 |
|---|---|---|
| 1차 보스전 관전 유실 | 전투 2분35초 전체를 관전했으나 기록 0. 에이전트가 "프로세스 상태 확인"을
하던 수 초 사이 보스가 죽었고, 로그는 종료 시 일괄 저장 구조라 비정상 종료(exit 1) 시 전체 유실 | ① 종료 시 일괄 저장 ②
에이전트(Hermes)의 관측 주기는 수 초 — 게임 16.6ms 프레임과 3자릿수 차이. 실시간 개입 구조 자체가 결함 |
| 이중 구동 사태 | 구동 1회 명령이 프로세스 2개(실행 계층의 쌍 생성)로 이어짐 →
에이전트가 한쪽을 종료했다가 전투 중 양쪽 모두 사망 | 단일 인스턴스 가드 부재 + 외부 프로세스를
에이전트가 직접 죽이는 운영 방식 |

**핵심 교훈**: 게임 루프(16.6ms)와 에이전트 대화 루프(수 초)의 시간 스케일이 다른 이상,
에이전트가 "타이밍을 맞춰" 개입하는 설계는 원리적으로 실패한다. **로봇이 스스로 실패를
처리하고, 에이전트는 결과를 검증하는 구조**로 바꿔야 한다 — 이것이 3번 항목의 설계 원리다.

## 2. 리서치 — 비교 기준선 (2025~2026 실시간 비전 에이전트 표준)

| 출처 | 핵심 패턴 |
|---|---|
| BetterCam / RapidShot / DXcam 벤치마크 (PyPI, 2025-26) | 화면 캡처는 GDI/mss가
아니라 **Desktop Duplication API**가 표준. mss 48fps vs DDA 계열 100~240fps |
| Vulkan ML Tutorial — Real-Time Camera Integration | **Producer-Consumer 3스레드
분리** (캡처/추론/렌더). 최신 프레임 overwrite + drop-oldest. UI·캡처가 추론에 절대 막히지 않음 |
| PaliGemma 실시간 패턴 (Medium, 2026-05) | 추론이 아무리 느려도 캡처 스레드는 하드웨어
속도 유지. **granular locking** — 락은 복사(μs)만 잡고 추론 중엔 안 잡음 |
| GetStream 실시간 비전 아키텍처 | 지연 대부분은 모델이 아니라 **캡처/디코딩/색변환** 단계.
스테일 프레임 drop, 우아한 성능 저하가 표준 |
| Stable-Baselines3 공식 문서 | PPO 추론은 CPU 권장, `deterministic=True` — 기존 구현이 이미
올바랐음 (유지) |

## 3. 정비 내역 — 코드 변경 4건 (전부 실측 검증)

### 3.1 캡처 계층 교체: mss → BetterCam (Desktop Duplication API)
- **실측**: mss 16.7ms/프레임(60fps 상한) → BetterCam **0.24ms** (≈70배, 변화 감지 시 수천 fps)
- 기존 M9_PIPELINE의 "R3 DXCam 검증" 목표를 사실상 초과 달성. DDA 계열로 통일.

### 3.2 아키텍처 재작성: 순차 단일 스레드 → 캡처/처리 분리
- `ScreenCapture`: 데몬 스레드가 60Hz로 grab, 최신 프레임만 슬롯 갱신 (latest-wins).
  처리 루프가 아무리 밀려도 캡처 지연이 누적되지 않음 — Vulkan 튜토리얼 패턴 그대로.
- 기존: grab → parse → predict → act가 1스레드 순차라 한 단계 막히면 전부 막힘.

### 3.3 데이터 무결성: 종료 시 일괄 저장 → 이중 증분 기록
- **JSONL**: 프레임 1줄씩 append + 30프레임마다 flush → 어떤 시점에 죽어도 직전 프레임까지 보존
- **스냅샷 JSON**: 5초마다 전체 재기록 (기존 분석 스크립트 호환)
- 1차 유실 사건의 직접 재발 방지책.

### 3.4 자율화: 보스전 종료 자동 감지 + 이중 구동 가드
- 전투 시작 → 종료(처치/사망/퇴장) 2초 후 **자동 기록 보존 + 종료** (`bossfight_ended`).
  에이전트/사람이 타이밍을 맞출 필요 제거 — "입장만 하면 됨".
- O_EXCL 배타적 파일락으로 쌍 프로세스 중 기록자 1개만 남김 (경쟁 안전, 죽은 락 자동 청소).
- `--record`: AI EYE 오버레이 MP4 동시 기록 (파서 관측값 + v7 결정 행동을 프레임마다 합성).

### 유지한 것 (이미 표준을 따르고 있었음)
- v7 PPO `deterministic=True` CPU 추론 (0.20ms — SB3 공식 권장과 일치)
- KILL 파일 킬스위치, 포커스 게이트, 관전 기본(키 미발화)
- v2.7 파서 (이중 레이아웃 + Practice 판별)

## 5. 남은 과제 (정비 범위 밖, 다음 세션 후보)

1. **관측 브리지 미구현 필드** — 제단 검출/보스 HP바/촛불 카운트 (현재 안전 기본값).
   v7이 정화(harvest) 판단을 하려면 제단 검출이 먼저.
2. **60fps 처리 루프** — 계산 여유 충분. 다만 파서가 플레이어 검출을 프레임마다
   하는 구조라 60fps 이득은 실측 필요.
3. **record_live.py 정리** — v3에 영상 기록 통합됨. 구 스크립트는 레거시로 보존 or 삭제.
4. 에이전트 운영 방식 — "에이전트가 프로세스를 죽이는" 개입을 금지하고
   로그/리포트 검증만 하도록 프로토콜 고정 (이번 사태의 운영적 교훈).
